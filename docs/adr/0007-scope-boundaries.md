# 0007. 合成器に徹し、隣接する機能を持たない

- 状態: 採用
- 日付: 2026-08-22

## 文脈

プロンプト管理の周りには隣接する機能が多い。語彙レイヤーがあれば音声認識の keyterm 設定を
そのまま出力できるし、ガバナンスレイヤーがあれば実行時に出力を検査する仕組みにも繋げられる。
どこまでを1つのライブラリで持つかを決めないと際限なく広がる。

## 決定

レイヤーを合成してプロンプト文字列を返すところまでを守備範囲とする。次は作らない。

- 音声認識（STT）の keyterm・カスタム語彙の出力
- 実行時ガードレール（出力の検査とブロック）
- eval・A-B テスト
- LLM の呼び出し
- レイヤー種別を利用者が足せるプラグイン機構

## 理由

- **STT の keyterm**: 語彙 YAML から Deepgram の keyterm を出すことは技術的にはできる。
  作らないのは、STT ごとに上限も形式も癖も違うため。Deepgram Nova-3 は1リクエスト最大100語で、
  語数を増やすと過剰にマッチして誤認識が増えるという性質がある。この調整を抱え込むと、
  ライブラリが音声基盤の設定管理に化ける。語彙レイヤーはプロンプト側の矯正
  （`misheard` を「こう書き起こされても同じ語」と示す指示）だけを担当する。
- **実行時ガードレール**: プロンプトに「してはいけない」と書くことと、出力を検査して止めることは
  別の仕事。後者は NeMo Guardrails・Guardrails AI・OpenAI Agents SDK の守備範囲で、
  合成したプロンプトと併用できる。
- **eval**: promptfoo がある。合成結果の文字列を渡せばそのまま使える。
- **LLM の呼び出し**: 呼ばないので、どのプロバイダ・どの実行基盤とも組み合わせられる。
- **プラグイン機構**: レイヤーの種類は5つに固定する。種類を足すときは整形関数を1本書けばよく、
  拡張点を用意するほうがコードが増える。

## 結果

依存が2つで済み、どの実行基盤にも載せられる。反面、語彙の正本をここに置いても STT 側の設定には
自動で反映されないため、音声チャネルを使う利用者は二重に管理することになる。
